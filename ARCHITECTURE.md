# Architecture

This is the law for **where code lives** in this repository: directory shape, file naming,
layer boundaries, and import direction. It is prescriptive, not a tour — if the tree drifts
from this document, either the tree or the document is wrong, and one of them gets fixed.

For *how* code is written (doc comments, function shape, types, error values) see `AGENTS.md`.
There is no `TESTING.md` yet — this document doesn't govern test placement until one exists.

Stack: Next.js 16 (App Router only), React 19, TypeScript 5 (`strict`), Drizzle ORM +
Postgres, NextAuth v5. Single package, no `src/` directory, npm.

## Naming

| Entity | Rule | Example |
|---|---|---|
| Files & directories | kebab-case, always | `match-card.tsx`, `tentacles/new/` |
| Dynamic route segment | framework-mandated brackets | `[id]/`, `[...nextauth]/` |
| Private route folder | `_name`, not routable | `onboarding/_components/` |
| Route group | `(name)`, omitted from URL | `(app)/`, `(auth)/` |
| React component (identifier) | PascalCase, matches default export | `export default function MatchCard()` in `match-card.tsx` |
| Server Action / lib function | camelCase verb phrase | `createTentacle`, `getMatches` |
| DB table (Drizzle) | camelCase export, snake_case column names | `export const tentacles = pgTable("tentacles", …)` |
| Type / interface | PascalCase, colocated with its source (schema-inferred where possible) | `type Subject` exported from `lib/db/schema.ts` |
| Env var | `SCREAMING_SNAKE_CASE`; `NEXT_PUBLIC_` prefix only if genuinely client-exposed | `DATABASE_URL`, `NEXT_PUBLIC_...` |
| Constant | `SCREAMING_SNAKE_CASE` at module scope | `TOTAL_SLOTS` in `lib/availability.ts` |

No camelCase or PascalCase filenames anywhere in this repo — that includes new files. No
spaces, no `(1)`-style suffixes, no ` copy` — those are duplicate-download artifacts, not
names; delete or properly rename on sight.

## Layers & import direction

Call stack: **entrypoint** (`page.tsx` / `layout.tsx` / `route.ts` / `app/actions/*.ts`) →
**domain logic** (`lib/*`) → **data access** (`lib/db`). This is already how most of the
codebase reads; don't insert an intermediate layer that's just a pass-through.

Enforced import rules:

1. Only `lib/db/index.ts` may `import` `drizzle-orm/postgres-js` or `postgres` and construct
   a client. Every other file that needs the database imports `db` (and, for standalone
   scripts, `client`) from `@/lib/db`.
2. A file whose first statement is `"use client"` may never import `@/lib/db`,
   `@/lib/queries`, or `@/lib/auth` — those are server-only. Pass data down as props instead.
3. `components/ui/**` may be imported from anywhere. `components/*` (non-`ui`) may be
   imported from `app/**`. Nothing under `lib/` imports from `app/` or `components/` — domain
   logic must be reachable without the framework or the UI layer.
4. Route-local code (a component or action used by exactly one route) is colocated in that
   route's private `_components/` or `_lib/` folder, not placed in the shared `components/`
   or `app/actions/` directories. The third time the same route-local shape is needed
   elsewhere, promote it to the shared location (see `AGENTS.md`'s "third occurrence" rule).
5. No deep relative imports (`../../../`). Use the `@/*` path alias, already configured in
   `tsconfig.json`.
6. No barrel files (`index.ts` re-exporting a directory) except `lib/db/index.ts`, whose job
   is specifically to be the sole client constructor.

## Size budgets

| Unit | Soft limit | Hard limit | Remedy when exceeded |
|---|---|---|---|
| `.tsx` file | 300 lines | 500 lines | Extract sub-components into the route's `_components/` (if route-local) or `components/` (if shared) |
| `.ts` file | 250 lines | 400 lines | Split by responsibility — one file already doing this well is `lib/queries.ts` at the read-query boundary |

Hard limit is enforced by CI (`scripts/check-architecture.mjs`); soft limit is a signal for
review, not a build failure. `lib/db/schema.ts` is exempt from both — a Drizzle schema file
grows with the data model, not with complexity.

## Decision recipes

- **New page/route**: create `app/<route>/page.tsx`. Keep it a thin composition of
  `components/*` and `app/actions/*`. If it needs page-specific sub-components, put them in
  a colocated `_components/` folder next to the page, not in shared `components/`.
- **New API route** (webhook, polling endpoint, non-form mutation): `app/api/<name>/route.ts`.
  If it's a form submission or simple mutation reachable via a Server Action instead, prefer
  the Server Action — Route Handlers here are for things a `<form>` can't express.
- **New DB query**: a one-off simple query stays inline in the action/route that needs it
  (matches the existing flat pattern). A query reused in 2+ places, or a raw-SQL query,
  goes in `lib/queries.ts` with a comment explaining what it computes (see `getMatches`).
- **New Server Action**: shared across routes → `app/actions/<domain>.ts` (create the file
  if the domain doesn't have one yet). Used by exactly one route → colocate as
  `app/<route>/actions.ts` or `app/<route>/_lib/actions.ts`.
- **New shared component**: `components/<name>.tsx`, kebab-case, one component's worth of
  responsibility. New shadcn primitive → `npx shadcn add <name>`, lands in `components/ui/`.
- **New domain/lib helper**: `lib/<name>.ts` if it's a new concern; add to an existing file
  (e.g. `lib/availability.ts`) if it's the same concern. Never add to a catch-all
  `utils.ts`/`helpers.ts` beyond what's already in `lib/utils.ts` (the `cn()` className
  helper) — name the file after what it does.
- **New background/standalone script** (seed, migration helper, one-off backfill):
  `drizzle/<name>.ts`, imports `{ db, client }` from `@/lib/db`, calls `client.end()` when done.
- **New env var / third-party SDK wrapper**: lives in the `lib/*` module that owns that
  concern (`lib/auth.ts` for auth secrets, `lib/uploadthing.ts` for the UploadThing SDK) —
  never read directly from a component or action.

## Anti-patterns

- **Constructing a DB client outside `lib/db/index.ts`.** Every extra `postgres(...)` call
  is a connection-pool leak waiting to happen and a second source of truth for `DATABASE_URL`
  handling.
- **Importing server-only modules into a `"use client"` file.** Leaks server secrets into
  the client bundle and defeats the point of the boundary.
- **A junk-drawer `utils/` or `helpers/` file that accumulates unrelated functions.** Name the
  file after the concern it owns instead.
- **Duplicate logic in a shared and a colocated location without a documented reason** (this
  repo had exactly this with two `joinWaitlist` implementations before this document existed —
  don't reintroduce it silently).
- **Hand-editing `drizzle/meta/**`.** It's `drizzle-kit`-generated; edit the schema and
  regenerate instead.
- **Files with spaces, `(1)`, or `copy` in the name.** These are artifacts of a duplicate
  download or a careless save, not real names — delete or `git mv` on sight.
- **Deep relative imports (`../../../`).** Use `@/*`.
